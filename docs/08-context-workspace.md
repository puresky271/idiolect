# 上下文工作区：四层在真实系统里的前后文

> 讲什么：四层之外的上下文骨架——12 层固定层序、预算裁剪、事实选择器的打分模型。 ｜ 前置：[`03-features.md`](03-features.md)；配套代码 [`idiolect/workspace.py`](../idiolect/workspace.py)。

**目录**：[1 工作区模式是什么](#1-工作区模式是什么) ｜ [2 一轮对话的完整装配结构](#2-一轮对话的完整装配结构) ｜ [3 本仓库的实现](#3-本仓库的实现) ｜ [4 事实工作区的打分模型](#4-事实工作区的打分模型) ｜ [5 与评测闭环的关系](#5-与评测闭环的关系)

本章提供上下文装配骨架，不附带长期记忆数据库、日程生成器或世界模拟服务。接入方负责提供有来源和权限边界的材料；不能把演示事实当作真实会话记忆。

## 1. 工作区模式是什么

四层 prompt 解决的是「这个角色该怎么说话」。但一个真实聊天系统里，模型每一轮
还需要知道很多**别的东西**：现在几点、角色在哪、刚才聊到哪、用户上周提过什么、
有哪些承诺还没兑现……这些材料每一轮都不同，而且加起来远超 prompt 预算。

**工作区（workspace）模式**的做法是：每一轮先把所有候选材料全部「摆到桌面上」
（收集成候选记录），按规则打分排序、按预算裁掉放不下的，最后按**固定层序**
装配成 messages。材料可以换、评分可以调，但层序永远不变——不变的结构才有
可评测性。

## 2. 一轮对话的完整装配结构

一套完整的聊天系统里，最终 messages 的典型结构（`ContextWorkspace` 的默认层序
`LAYER_ORDER` 即按此排列）：

| # | 层 | 内容 | idiolect 对应 |
|---|---|---|---|
| 1 | `persona` | 人格 prompt | **idiolect 的四层装配就在这里** |
| 2 | `historical_recap` | 历史聊天摘要 | — |
| 3 | `current_state` | 角色此刻状态：位置、日程、天气、心情 | — |
| 4 | `interlocutor_state` | 对话方（用户/同住角色）的状态 | — |
| 5 | `proactive_continuity` | 主动连续性：上次说到哪、待续的话头 | — |
| 6 | `fact_workspace` | 事实工作区：本轮打分选出的事实卡（第 4 节） | `select_facts` 的产出 |
| 7 | `memory_recall` | 记忆召回 | — |
| 8 | `cluster_memory` | 聚类记忆（长程主题簇） | — |
| 9 | `conversation_arc` | 对话弧线：本场对话走到哪个阶段 | — |
| 10 | `on_demand_evidence` | 按需证据：用户问起才现查的细节 | — |
| 11 | `cognitive` | 认知指令 | — |
| 12 | `recent_dialogue_guard` | 最近对话护栏：防复读、防与上句矛盾 | — |

之后是 user/assistant 交替的**对话历史**；最后，本轮执行指令
（`execution_packet`：长度预算、风格提醒）不单独成块，而是**追加到本轮那条
user 消息的末尾**——那条才是模型要回答的输入，也是离生成端最近的位置，最不容易
被长 prompt 稀释。装配出来的 messages 形如：

```text
[ system(persona) … system(recent_dialogue_guard),
  user(上一轮), assistant(上一轮),
  user(本轮 + 执行包) ]        ← 执行包在这里
```

顺序的设计原则和四层一致：稳定前缀在前（缓存命中），动态上下文居中，
执行指令贴近生成端。

## 3. 本仓库的实现

`idiolect/workspace.py`（零第三方依赖）：

- **`ContextWorkspace` / `assemble`**：12 层固定层序、空块剔除、整体字符预算
  （从层序尾部开始**整块摘除**未 pinned 的块——切半块上下文比整块缺失更难
  排查）；同一层可以多次 `add()`，默认**追加合并**（两路召回都写 `memory_recall`
  是常态），要整块换掉得显式传 `replace=True`。它自带的 `execution_packet` 只会
  贴到**已装配的最后一条 user**（也就是历史里的上一轮）；本轮那句话还没进来时
  请不要用它，`build_workspace_messages` 会负责贴（见下）。给了包却没有可贴的
  user 时它**直接报错**，不静默丢弃；pinned 层自己超预算时发 `RuntimeWarning`，
  也不静默超发。
- **`build_workspace_messages`**：一行入口，idiolect 四层进 persona 位
  （pinned，不可裁剪、不可被外部块覆盖），外部材料挂其余层位，`execution_packet`
  贴到本轮 user 上：

```python
from idiolect.workspace import build_workspace_messages
messages = build_workspace_messages(
    "乐奈", "你今天又想去哪找猫",
    blocks=[("current_state", "乐奈在 RiNG 排练室，下午没课"),
            ("fact_workspace", "用户上周提过想养猫")],
    history=[{"role": "user", "content": "在干嘛"},
             {"role": "assistant", "content": "练习。"}],
    execution_packet="【本轮执行】回复 ≤19 字",
)
# messages[-1] == {"role": "user",
#                  "content": "你今天又想去哪找猫\n\n【本轮执行】回复 ≤19 字"}
```

- **`select_facts`**：事实选择器（第 4 节的打分模型，词面通道部分）。

## 4. 事实工作区的打分模型

候选事实可以来自十几路渠道（对话事实卡、当日事实、历史摘要、记忆召回、
gossip、工具产出、外部证据……），每条按四个维度记分。以下常量都是实测调校值，
不是理论拍脑袋。

**词面重叠**（门槛）：查询与事实的 2/3-gram 词表求交，
`min(12, Σmin(4,词长)/2 + 0.65×交集大小)`。单个共享 bigram 得 1.65、
trigram 得 2.15；**2.0 是强弱边界**——低于它保留参选资格，但拿不到任何
加权（泛词碰撞会靠渠道/类型加权的堆叠混进前排）。停用词表把
「今天/最近/什么时候」这类词排除在话题证据之外：它们是路由信号，不是内容——
而且要把分词器可能切出的每个 2/3-gram 也一起排除，否则长 CJK 串会经子串
把它们带回来。

> ⚠️ **词面通道的已知盲区：单个汉字不成词。** 分词正则要求 ≥2 个 CJK 字符，
> 所以「猫」「雨」「伞」这类一字话题产不出 token，重叠分直接 0，那条事实在
> 词面通道里等于不存在——对乐奈这种以「猫」为核心的语域是实打实的漏召回。
> 补法是向量通道（本仓库未收录）或在词表里写双字形式（「野猫」「下雨」）。
> 放宽分词口径会让上面那批实测调校值失效，所以这里只记录，不擅自改。

**渠道加权**：`schedule_recall 2.2 > turn_fact 2.0 > today_fact 1.6 >
memory_recall 0.8 > gossip -0.2`。memory_recall 曾是 0.2，真实聊天日志里
0/10 条记忆能被选中——加权是被线上分布教出来的，不是理论值。

**类型加权**：`correction 9.0 > commitment 6.5 > open_thread 5.0 > fact 1.0`。
「改成周六了」必须压过「约在周五」，「答应帮你带」不能沉底。

**新近度**：相对候选集最新记录分六档（15 分钟内 2.5 → 两周以上 0.1）。

之后还有排序、近去重、条数（10）与字符（3200）双预算。

**本仓库没有实现的**（各自依赖更大的运行时设施）：

- **语义向量通道**：句向量模型对全部候选算一次余弦，≥0.65 直通、<0.40 丢弃、
  中间地带不采信。要解决的是「猫去哪了」对「用户喜欢猫」这种零词面重叠的
  真召回——词面通道在这类对上结构性失明。
- **纠偏取代**：跨渠道的「改成/改为/纠正」解析，让旧值记录失效。
- **注入记账与复读治理**：记录每条事实被注入过几次、模型用没用，下轮降权。
- **级联折叠**：已被聚类概括覆盖的原始记录不再占预算。

## 5. 与评测闭环的关系

工作区让「该看的材料」也变成可评测对象：候选集固定 → 选择结果确定 →
注入内容可 diff。改打分参数与改四层同纪律：先 dump 基线、改后再 dump、
逐场景审 diff（见 `docs/04-evaluation.md` 与 `docs/05-tooling.md`）。
