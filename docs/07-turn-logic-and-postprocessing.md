# turn_logic 与后处理：怎么搭，以及为什么这么搭

> 讲什么：两个动态部件——turn_logic（这一轮该做什么）与 voice_check（回复出门前的那道处理）的搭建流程与契约边界。 ｜ 前置：[`03-features.md`](03-features.md) 的五类特征。

**目录**：[1 turn_logic](#1-turn_logic) ｜ [2 后处理（voice_check）](#2-后处理voice_check) ｜ [3 加东西的清单](#3-加东西的清单) ｜ [4 反思](#4-反思)

前面几篇讲的是「静态特征怎么落进 prompt」。这一篇讲两个动态部件：**turn_logic**（这一轮该做什么）和 **voice_check**（回复出门前的那道处理）。

## 1. turn_logic

### 1.1 它在哪一层

四层里的第四层，也是唯一「命中才注入」的一层。一次装配里：

- 命中场景 → 该场景的正文被追加到 system 末尾；
- 同一 session 内同一场景只注入一次（`scene_engine._mark_fired`）；
- 一轮最多注入 2 个场景（`build_scene_blocks(max_blocks=2)`），因为场景词表有重叠（「雨」同时属于猫话题和吉他话题）。

不重复注入的理由是长会话：同一段指引每轮都出现，会把角色的语气压成一个方向。上限 2 的理由是预算与被覆盖——两个场景指引叠在一起时，模型往往只执行后一个。

### 1.2 三层分工

| 层 | 位置 | 负责 |
|---|---|---|
| 通用场景层 | `idiolect/general_scenes.py`（13 个 × 5 角色） | 五个人共有的语用场景：情绪崩溃、被安慰、状态差、只祝愿别人、日程、求助、事实问答、闲聊、问「你刚才那句什么意思」、试探态度、聊第三方 |
| 角色专属场景层 | `idiolect/characters/<key>/turn_logic/scenes.py` | 只有这个人会遇到的场景：吉他/演出、红茶、熊猫、编曲、美妆…… |
| 主题深模块 | 同目录下的单文件模块（如 `space.py`、`nap.py`、`home.py`） | 一个话题的完整行为准则：外婆的店、打瞌睡、家里的旧事 |

通用场景层是后来补的，因为它曾经是最差的那一批：`affection`（被示好）在两条探针臂里都是最低分——立希中位 2 字（参照 12）＝过度沉默，灯中位 50 字（参照 10）＝过度铺陈。同一个场景、两个方向都能错，说明它不是长度目标能压住的，需要场景级指引。

### 1.3 搭建流程

**第一步：先定场景，不要先写文案。** 候选来自探针的 `excess` 排序（本场景偏离 − 该角色平均偏离），正值得高的就是要处理的。凭直觉挑场景的结果通常是把已经正常的场景改坏。

**第二步：判断该不该加模块。** 判据是「长度目标能不能解决」：

- 长度目标能解决 → 不加模块（例如「这一轮该说 16 字」，模型照做即可）；
- 长度目标解决不了 → 加模块。过度沉默与过度铺陈同时出现在同一场景，就是这种情况。

**第三步：找参照物。** 两种口径，都要看：

- **原型检索**：给场景写一句原型台词，用句向量取近邻。问题是短句语料上会被长度和风格带偏——`affection` 用纯检索给灯抓来的近邻是「今天有体育课」。
- **反应词典锚定**：先按该场景的反应词筛候选，再统计。`affection` 改用它之后，锚定中位与检索同向（灯 10 vs 12、素世 17 vs 17），说明锚定没有扭曲分布。

两种口径差别大时，以反应词典为准，并在模块头部记下两套数字与差异原因。

**第四步：写正文。** 结构固定成三块：

1. 这一轮对方在做什么（一句话，用人话，不引用统计）；
2. 你该做什么（可执行的动作，不是态度词）；
3. 分寸 bullet：不该做什么、做到什么程度、以及**边界情形**（对方只在开玩笑时怎么办、提到第三方时怎么办）。

正文里不许出现可整句照抄的例句（见 `docs/03-features.md` 第 5 节）。要举例就写形态描述，或者给一个「占位槽」形式（「（具体物/动作）+ 我自己的反应」）。canon 原话改成「从你自己的档案里取」。

口癖只从 `data/tic_by_scene.json` 的显著项里取（`lift` ≥ 1.4 且 cell 内 ≥ 5 次），填进 `SceneModule.tics`；凭感觉填的口癖会让场景指引变成风格污染。

**第五步：定触发词。** 三条纪律：

- 语料实证：语料里不存在的词不许当触发词（`tools/distill/verify_triggers.py`）；
- 容易误触发的用与逻辑（`all_required=True` + lookahead），例如「示好信号」与「第二人称指向」必须同时命中；
- 注入层可以比分类器更紧。分类器把「你是不是又睡着了」判成「试探态度」，注入层必须挡住它——那句话有专门的场景模块。

触发词是**正则片段**，`SceneModule.pattern()` 直接编译，不要再 `re.escape`（踩过一次：「(昨天|上次)」被转义成字面量，与逻辑整体失效，场景静默不触发）。

**第六步：接线。** 一个模块要能被调用，需要：

```text
SceneModule(...)  →  角色包 turn_logic/__init__.py 的模块列表
                  →  build_scene_blocks(user_text, modules, session_id=…)
                  →  <char>/api.py::render_supplemental_blocks
                  →  idiolect/registry.py::render_turn_special_block
                  →  idiolect/assemble.py（第四层）
```

每一层都要有 env 开关：`<PREFIX>_TURN_LOGIC_<KEY>_ENABLED=0` 关闭单个模块。回退开关不是装饰——before/after 两臂靠它产出，没有它就做不了 prompt diff 门禁。

**第七步：门禁。** 改完至少跑四件：

1. `tools/gates/dump_turn_logic_gate.py --phase after`：触发矩阵（该命中的命中、不该命中的不命中）、归属标记（新模块的标题必须出现）、角色串味（素世的块不得出现在乐奈的渲染里）；
2. `tools/gates/_tl_deep_check.py`：正文规范（无可照抄例句、正反例标记齐全）；
3. `tools/gates/dump_prompt.py --phase before/after`：两臂对照，确认无关场景零漂移；
4. `tools/offline_smoke.py`：全量体检。

### 1.4 什么时候**不该**加模块

- 长度目标能解决时（它会白白占掉一轮 2 个 block 的配额）；
- 场景在探针里不可测时（例如需要可指代上文的「你刚才那句什么意思」，占位夹具没有上文，加了也验证不了）；
- 只为了「更保险」而加时。每加一条约束都会挤掉别的约束的注意力，`docs/06-lessons.md` 里那条「约束之间会互相吞掉」就是这么来的。

## 2. 后处理（voice_check）

### 2.1 它解决什么

prompt 侧改不动、或者改了不划算的那部分问题。典型例子：乐奈的冗余起手「嗯。」。

原作统计摆在那里：她 55% 的回合以名词直出，只有 8% 用语气词起手；而生产臂把这两项推成 19% / 67%（旧批次记录）。prompt 侧做过两次 A/B，效果不显著；而这条规则可以在出站时确定性地执行。于是把它做成后处理。

按当前 `repo_standalone` 批次实测是 **24% / 57%**（`tools/score/_noun_initial.py <批次名>` 会把原作基线与当前臂并排打出）：方向仍然反着——她该以名词起手，却被推去用语气词，只是没有旧批次那么极端。

### 2.2 契约边界：无损与有损必须分开

这是最容易写错的地方。

| 层 | 函数 | 允许做什么 |
|---|---|---|
| 无损清洗 | `voice_check.clean_reply` | 只做不改语义的替换：超配额感叹号降级、连排句号归一、省略号归一 |
| 风格改写 | `voice_check.opener.strip_redundant_ack` | 会**删字**（去掉冗余起手），必须在 API 层显式调用 |

`clean_reply` 一旦开始删字，「回复无损」这条契约就没了，切分与显示的链路会跟着出问题。所以风格改写一律放在 `idiolect/characters/<key>/api.py` 的 `post_reply_voice_check` 里，并配独立开关。

### 2.3 搭建流程

**第一步：确认 prompt 侧改不动。** 先试 prompt（加约束、给反例、调长度目标），有效就不用做后处理。后处理是最后手段，因为它不改变模型的意愿，只是把结果修一修。

**第二步：从原作统计里找规则。** 规则的形状必须能被语料证实，例如：

- 名词直出 55% / 语气词起手 8% → 「内容够长时去掉冗余起手」；
- 短行（≤6 字）里名词直出 54% / 语气词 9% → 短确认不动（「嗯。开心」是对的，删了就变味）；
- 剩下的 33% 是语料里确有的短确认形态 → 明确不处理。

**第三步：设阈值并写清例外。** 例：`MIN_REST = 4`，即删掉起手后正文必须还有 ≥ 4 字才动手；起手本身是疑问（「嗯？」）不动。

**第四步：判据是「对原作近乎 no-op」。** 把规则拿去跑原作语料：如果它改写了大量原作台词，说明它在改风格而不是去冗余。乐奈那条只改到 4% 的行，名词起手率不降——这才叫「去冗余」。

**第五步：诊断与改写分开。** 阈值告警（中位 6 字 / p90 12 字 / 硬上限 16）只报不改，交给评测侧统计；改写只做规则明确的那几条。诊断项包括助手腔、越界（关系承诺、元叙述、心理归因、工整收束、客服腔、视觉声称）。

**第六步：开关 + 测试。** 每条改写规则一个 env flag；测试锁「短确认不动、疑问不动、够长才动」这三个边界。

### 2.4 各角色的后处理模块

| 角色 | 模块 |
|---|---|
| 灯 | 省略号配额、成对省略号、大停顿独立成泡、感叹号软化、起手节流、标点归一、气泡扩展、や/あ 重复 |
| 爱音 | 省略号、语气词断句 |
| 立希 | 装饰音、语尾助词、软化回应 |
| 素世 | 称呼归一、标点、语气判定、阈值 |
| 乐奈 | 冗余起手、标点、语气判定、阈值 |

公共基调判定在 `idiolect/tone.py`：把「存在宣言 / 元评论 / 读心 / 格言化」等语气类别标出来，供各角色的 voice_check 与诊断共用。它的字面模式对人工标注实例的召回是 33%（6/18），所以只用于诊断统计，不作硬拦截。

## 3. 加东西的清单

**加一个 turn_logic 场景模块**

1. 从探针 `excess` 排序里确认它是待处理场景；
2. 确认长度目标解决不了；
3. 找参照物（检索 + 反应词典两套口径）；
4. 写正文（三块结构、零例句、口癖取自 `tic_by_scene`）；
5. 定触发词（语料实证、必要时与逻辑）；
6. 接线到角色包 + env 开关；
7. 跑门禁四件套。

**加一条后处理规则**

1. 确认 prompt 侧改不动；
2. 规则形状有原作统计支持；
3. 定阈值与例外；
4. 对原作语料跑一遍，确认近乎 no-op；
5. 放进 API 层（不是 `clean_reply`），加开关；
6. 补三边界测试。

## 4. 反思

- **动态层的收益不如静态层稳定。** 静态层（canon、语气清单、说话尺度）每次改动都在池化数据上留下正效应；动态层的效果依赖触发是否命中，而触发的召回与精度本身就难做。所以 turn_logic 的验收标准不是「加了模块」，而是「触发矩阵通过 + 该场景的 excess 下降」。
- **模块数不是越多越好。** 一轮最多两个 block，模块越多，真正生效的那两个越不确定。宁可把相邻场景合并成一个大场景，也不要为每个细分情境开一个模块。
- **后处理的边界要靠测试守。** 「无损」是一条会被慢慢侵蚀的契约：每加一条「顺手删掉」的规则都在削弱它。`clean_reply` 与风格改写的分工必须有测试锁住。
